Nós vamos apresentar o projeto da disciplina de Desenvolvimento Web Back-end: a Clínica API, um sistema de agendamento de consultas. O projeto é uma API RESTful integrada a um banco de dados relacional, com um servidor WebSocket no mesmo projeto.

[Slide 2] O grupo tem sete integrantes, e cada um vai apresentar uma parte: requisitos, entidades, as rotas da API, o WebSocket e os testes.

[Slide 3] O domínio escolhido é o agendamento de consultas em uma clínica médica. A API permite cadastrar especialidades, médicos e pacientes, agendar consultas e acompanhar o atendimento no dia: a recepção chama o paciente, o médico inicia o atendimento e depois encerra. Na sala de espera existe um painel de atendimento, que recebe as chamadas pelo WebSocket e mostra o nome do paciente, o consultório e a situação de cada sala.

Usamos Java 21 com Spring Boot 3.5: Spring Web para as rotas, Spring Data JPA com Hibernate como ORM, Spring WebSocket e Bean Validation. O banco é o H2, salvo em arquivo. A documentação interativa é gerada pelo Swagger, os testes foram feitos no Postman e o código está versionado com Git.

[Slide 4] O código é organizado em camadas: os controllers expõem as rotas, os services têm as regras de negócio, os repositories acessam o banco, e as pastas de DTO, exceções e WebSocket completam o projeto. As telas de recepção e painel são servidas pela própria aplicação. Agora o Pedro vai apresentar os requisitos.

[Slide 5] Definimos onze requisitos funcionais para a API. Do RF01 ao RF05 temos o CRUD completo, ou seja, cadastrar, listar, consultar, atualizar e excluir, de especialidades, médicos, pacientes e consultas. O RF03 trata do vínculo entre médicos e especialidades. O RF06 permite filtrar consultas por data, médico, paciente e status, e o RF07 lista a agenda de um médico e o histórico de um paciente.

Também temos regras de negócio: o RF08 impede duas consultas no mesmo horário para o mesmo médico ou paciente; o RF09 controla o status da consulta, que pode ser agendada, chamada, em atendimento, concluída ou cancelada, aceitando só as transições do diagrama de estados; o RF10 não deixa excluir médicos ou pacientes que tenham consultas; e o RF11 garante que todos os erros voltem no mesmo formato.

[Slide 6] O requisito do WebSocket é o RF-WS01, o painel de atendimento em tempo real. Quando a recepção chama um paciente pela rota POST /api/consultas/{id}/chamar, o servidor envia uma mensagem pelo WebSocket /ws/painel para todos os clientes conectados. O painel mostra o paciente, o consultório e o médico, guarda as últimas chamadas e pode emitir um aviso sonoro. As outras mudanças de status também são enviadas, então o painel atualiza a situação de cada sala e a tela da recepção se atualiza sem recarregar. À direita está um exemplo da mensagem em JSON. Agora o Vitor apresenta as entidades.

[Slide 7] O sistema tem quatro entidades: Especialidade, com nome único e descrição; Médico, com nome, CRM único, e-mail, telefone e a sala onde atende; Paciente, com nome, CPF único, data de nascimento, telefone e e-mail; e Consulta, com data e hora, status, observações e as chaves estrangeiras do médico e do paciente.

Entre elas existem três relacionamentos. Médico e Especialidade é muitos-para-muitos: um médico pode ter várias especialidades e uma especialidade pode ter vários médicos. Médico e Consulta é um-para-muitos: um médico atende várias consultas e cada consulta tem um único médico. E Paciente e Consulta também é um-para-muitos.

[Slide 8] Este é o diagrama entidade-relacionamento do banco gerado pelo Hibernate. Dá para ver a tabela de ligação medico_especialidade, com as duas chaves, e a tabela consulta com medico_id e paciente_id.

[Slide 9] No código, o muitos-para-muitos foi feito com @ManyToMany e @JoinTable na classe Medico, que é o lado dono, e mappedBy na classe Especialidade. O um-para-muitos usa @OneToMany(mappedBy = "medico") no Médico e @ManyToOne com @JoinColumn na Consulta; o mesmo vale para o Paciente.

[Slide 10] Para mostrar que isso existe no banco, abrimos o console do H2. As tabelas foram criadas pelo Hibernate. A primeira consulta junta médicos e especialidades pela tabela de ligação, que é o muitos-para-muitos; a segunda mostra as consultas com as chaves do médico e do paciente, que é o um-para-muitos. Agora o Lygio apresenta as rotas.

A API segue o estilo RESTful, com URL base localhost:8080/api. Para cada rota documentamos o verbo HTTP, o path, o corpo de requisição, o corpo de retorno e os status de sucesso e de erro, como pede a especificação.

[Slide 11] Em Especialidades temos o CRUD completo: GET para listar e buscar por id, POST para cadastrar, que retorna 201, PUT para atualizar e DELETE, que retorna 204. Se o nome vier vazio a API devolve 400, se o nome já existir devolve 409, e se o id não existir devolve 404. Também existe a rota que lista os médicos de uma especialidade.

[Slide 12] Em Médicos o CRUD é igual, e no cadastro já podemos mandar a lista de especialidades. O CRM não pode se repetir, e um médico com consultas não pode ser excluído: nesses casos a API responde 409. Aqui também estão as rotas do relacionamento muitos-para-muitos: listar as especialidades do médico, vincular uma especialidade com POST e desvincular com DELETE. E a rota /medicos/{id}/consultas mostra a agenda do médico, que é o um-para-muitos.

[Demonstração] Vou mostrar no Swagger: cadastro uma especialidade e recebo 201; listo e atualizo; vinculo essa especialidade ao médico 1 e listo os médicos dessa especialidade; depois desvinculo e excluo, recebendo 204. Agora o Vagner apresenta pacientes e consultas.

[Slide 13] Em Pacientes temos o mesmo CRUD: listar, buscar, cadastrar, atualizar e excluir. O CPF é validado no formato e não pode se repetir; se repetir, a API devolve 409. E um paciente que tem consultas não pode ser excluído. A rota /pacientes/{id}/consultas mostra o histórico do paciente, o outro lado do um-para-muitos.

[Slide 14] Consultas é a entidade central. Além do CRUD, a listagem aceita filtros por data, médico, paciente e status. Para agendar enviamos data e hora, o médico, o paciente e as observações. Se o médico ou o paciente não existir a resposta é 404, e se o horário já estiver ocupado a resposta é 409. Temos ainda duas rotas de atendimento: o PATCH de status e o POST de chamar, e as duas avisam o painel pelo WebSocket.

[Slide 15] Este é o ciclo de vida da consulta. Ela nasce AGENDADA, pode ser CHAMADA, passa para EM_ATENDIMENTO e termina CONCLUIDA, ou pode ser CANCELADA. Se o paciente não comparecer, a consulta chamada volta para agendada. Qualquer transição fora do diagrama é recusada com 409, por exemplo concluir uma consulta que ainda nem foi atendida. Todos os erros seguem o mesmo formato: data e hora, status, mensagem, caminho e os campos inválidos.

[Demonstração] No Swagger: cadastro um paciente e recebo 201; tento o mesmo CPF e recebo 409. Agendo uma consulta e recebo 201; tento outra no mesmo horário com o mesmo médico e recebo 409. Por fim, tento concluir uma consulta agendada e a API recusa com 409. Agora o Guilherme mostra o WebSocket.

[Slide 16] O servidor WebSocket fica no endpoint /ws/painel e foi feito com o Spring WebSocket. O servidor envia dois tipos de mensagem para os clientes: CHAMADA, quando um paciente é chamado, e STATUS, para as outras mudanças. O cliente pode mandar “ping” e recebe “pong” para testar a conexão.

A classe PainelWebSocketHandler guarda todas as sessões abertas e faz o broadcast, mandando a mesma mensagem para todo mundo. A classe PainelNotifier converte a consulta em JSON e só envia depois que a alteração é gravada no banco, no commit. O diagrama mostra esse fluxo: a recepção faz o POST de chamar, a API busca a consulta, atualiza o status, faz o commit e então envia o evento para o painel e para a recepção.
