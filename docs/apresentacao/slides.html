Agendamento de consultas em uma clínica médica

A API permite cadastrar especialidades, médicos e pacientes, agendar consultas e acompanhar o atendimento no dia: a recepção chama o paciente, o médico inicia o atendimento e depois o encerra.

A clínica possui um painel de atendimento na sala de espera. Ele recebe as chamadas por WebSocket e mostra o nome do paciente, o consultório e a situação de cada sala.

Estilo da API: RESTful, com servidor WebSocket integrado no mesmo projeto.

Tecnologias utilizadas

  • Java 21 · Spring Boot 3.5
  • Spring Web · Spring Data JPA · Spring WebSocket · Bean Validation
  • Hibernate (ORM) · banco relacional H2 (arquivo)
  • springdoc-openapi (Swagger UI)
  • Postman (testes funcionais)
  • Git (versionamento)

RF-WS01: painel de atendimento em tempo real

Quando a recepção chama um paciente pela rota POST /api/consultas/{id}/chamar, o servidor envia uma mensagem no WebSocket ws://localhost:8080/ws/painel para todos os clientes conectados.

  • O painel exibe paciente, consultório e médico
  • Mantém a lista das últimas chamadas e pode emitir aviso sonoro
  • As demais mudanças de status também são enviadas: o painel atualiza cada consultório e a recepção se atualiza sem recarregar
// mensagem enviada pelo servidor
{
  "tipo": "CHAMADA",
  "momento": "2026-11-10T09:31:05",
  "consulta": {
    "id": 2,
    "dataHora": "2026-11-10T09:30:00",
    "status": "CHAMADA",
    "observacoes": "Febre há 2 dias",
    "medico": { "id": 2, "nome": "Dr. Bruno Lima",
                "sala": "Sala 2" },
    "paciente": { "id": 3, "nome": "Pedro Santos" }
  }
}
Clínica API · BRADWBK6
Entidades do domínioApresenta: Vitor

Quatro entidades

Especialidade

id, nome (único), descricao

Medico

id, nome, crm (único), email, telefone, sala

Paciente

id, nome, cpf (único), dataNascimento, telefone, email

Consulta

id, dataHora, status, observacoes, medico_id (FK), paciente_id (FK)

Relacionamentos

  • Médico ↔ Especialidade (muitos-para-muitos): um médico pode ter várias especialidades e uma especialidade pode ter vários médicos. Tabela de ligação medico_especialidade.
  • Médico → Consulta (um-para-muitos): um médico atende várias consultas; cada consulta tem um único médico (consulta.medico_id).
  • Paciente → Consulta (um-para-muitos): um paciente tem várias consultas; cada consulta pertence a um único paciente (consulta.paciente_id).

Mapeamento dos relacionamentos no código

Medico.java

// Muitos-para-Muitos (lado dono)
@ManyToMany
@JoinTable(
    name = "medico_especialidade",
    joinColumns = @JoinColumn(name = "medico_id"),
    inverseJoinColumns =
        @JoinColumn(name = "especialidade_id"))
private Set<Especialidade> especialidades;

// Um-para-Muitos
@OneToMany(mappedBy = "medico")
private List<Consulta> consultas;

Especialidade.java

// lado inverso do N:N
@ManyToMany(mappedBy = "especialidades")
private Set<Medico> medicos;

Consulta.java

// lado "muitos" do 1:N
@ManyToOne(optional = false)
@JoinColumn(name = "medico_id")
private Medico medico;

@ManyToOne(optional = false)
@JoinColumn(name = "paciente_id")
private Paciente paciente;

Regras de negócioApresenta: Vagner

Ciclo de vida da consulta e tratamento de erros

  • Transição fora do diagrama → 409 (ex.: concluir consulta ainda não atendida)
  • Mesmo médico ou paciente no mesmo horário → 409
  • Excluir médico/paciente com consultas → 409
  • Concluídas ou canceladas não podem ser alteradas
// formato único de erro (RF11)
{ "timestamp": "2026-11-10T10:00:00", "status": 400,
  "erro": "Bad Request",
  "mensagem": "Dados inválidos na requisição",
  "path": "/api/pacientes",
  "campos": { "cpf": "deve estar no formato 000.000.000-00" } }
